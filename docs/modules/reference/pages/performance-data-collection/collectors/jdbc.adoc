
= JDBC Collector
:description: Learn how to configure and use the JDBCCollector in OpenNMS {page-component-title} to collect performance data via JDBC drivers.

The JDBCCollector collects performance data via JDBC drivers.
Attributes are retrieved using SQL queries.
The JDBC driver for PostgreSQL is included with {page-component-title}.
Any other JDBC drivers must be manually loaded to collect from other types of database servers (see xref:deployment:core/installing-jdbc-driver.adoc[] and xref:deployment:minion/installing-jdbc-driver.adoc[]).

== Collector facts

[options="autowidth"]
|===
| Class Name            | `org.opennms.netmgt.collectd.JdbcCollector`
| Package               | core
| Supported on Minion   | Yes (see limitations)
| Configuration         | Stored in the database; see <<jdbc-collection-storage, JDBC collection configuration>>
|===

=== Limitations on Minion

No JDBC drivers are included with Minion.
To install a JDBC driver, follow the steps in the xref:deployment:minion/installing-jdbc-driver.adoc[Installation JDBC driver on the Minion] page.

When running on Minion, you also cannot reference the data sources in `opennms-datasources.xml`.
Instead, you must use the service parameters to set the JDBC connection settings.

== JDBC collection configuration

Understanding xref:operation:deep-dive/performance-data-collection/resource-types.adoc#resource-types[resource types] helps when defining JDBC collections.

[[jdbc-collection-storage]]
=== Storage

JDBC collections are stored in the database and are created and edited through the <<jdbc-collection-ui, web UI>> or the xref:development:rest/jdbc-datacollection-rest-api.adoc[JDBC Data Collection REST API].
Editing `$\{OPENNMS_HOME}/etc/jdbc-datacollection-config.xml` or the files in `$\{OPENNMS_HOME}/etc/jdbc-datacollection.d/` has no effect: their contents are migrated into the database during the upgrade (see <<jdbc-collection-upgrade>>), and the files are no longer read.

The configuration is split into sources:

* The source `default` holds what used to be `jdbc-datacollection-config.xml`.
* Every former file `jdbc-datacollection.d/<name>.xml` became a source named `<name>`, such as `postgresql` or `mysql`.
* A source holds JDBC collections and an RRD repository.
* A collection holds the RRD step and round robin archives, and the SQL queries to run.
* A query holds the SQL statement and the result columns to store.

A collectd service selects one collection through its `collection` parameter.
The collector merges all sources into one list: `default` first, then the other sources sorted by ID.
A collection name must therefore be unique across all sources.
If a collection name appears in more than one source, the collector uses the first one and ignores the others; the web UI marks an ignored collection.
The collector uses the RRD repository of the first source that sets one, normally `default`, for all collections.

The collector reads the configuration on every collection, so a saved change applies from the next collection on; no reload or restart is needed.

Reading and changing the configuration requires the `ROLE_ADMIN` role, because it holds the SQL statements that the collector runs.

NOTE: The configuration is also available as `jdbc-datacollection-config` in the xref:development:rest/config_management.adoc[Config Management REST API] at `/rest/cm/jdbc-datacollection-config`, where each source is a configuration ID.

[[jdbc-collection-ui]]
=== Manage JDBC collections in the web UI

. Log in to the web UI as a user with the `ROLE_ADMIN` role.
. Click menu:Administration[Configure JDBC Data Collection] in the side menu.
. Or, click menu:Administration[Configure OpenNMS] in the side menu, then click menu:Performance Measurement[Configure JDBC Data Collection].

The page has two tabs:

Sources::
Lists the sources in the order the collector merges them.
Click *New source* to create a source, or open a source to edit it.
Any source except `default` can be deleted together with all of its collections.

Import::
Upload a file to store it as a source: an XML file in the format of the former `jdbc-datacollection.d/*.xml` files, for example a file from `$\{OPENNMS_HOME}/etc_archive/`, or a JSON file downloaded from a source.
The source ID is taken from the *Source id* field or, when it is empty, from the file name; a timestamp suffix of an archived file, such as `mysql.xml.20261110120000`, is removed.
An existing source is replaced only when *Replace an existing source* is enabled.

The page of a source shows its RRD repository, which you can change, and its collections.
Use *Download XML* or *Download JSON* to download the source as a file, and *Delete source* to delete it.
For each collection, the *Used by* column lists the collectd services that use it, as `package/service`.
A collection that is ignored because an earlier source defines a collection of the same name is marked `Ignored: also defined in '<source>'`.

Open a collection to edit its name, its RRD step and round robin archives (for example, `RRA:AVERAGE:0.5:1:2016`), and its queries.
For each query you set:

* A name that is unique within the collection.
* The recheck interval, in milliseconds.
* The interface type, such as `ignore` for node-level values or `all`.
* A resource type and an instance column, set together for a query that returns more than one row; each row becomes a resource of that type, identified by the value of the instance column.
* The SQL statement.
* The columns to store, each with its name, the column label in the result set if it differs from the name, its type (`gauge`, `counter` or `string`), and an alias of at most 19 characters that is unique within the query.

These rules apply to collections:

* Renaming a collection does not change the `collection` parameter of the collectd services that use it.
Update the services in `collectd-configuration.xml` as well.
* Deleting a collection that collectd services use stops these services from collecting; the confirmation dialog lists them.

[[jdbc-collection-upgrade]]
=== Upgrade from XML files

Earlier versions read the collections from `$\{OPENNMS_HOME}/etc/jdbc-datacollection-config.xml` and `$\{OPENNMS_HOME}/etc/jdbc-datacollection.d/*.xml`.
The upgrade imports these files once:

* `jdbc-datacollection-config.xml` becomes the source `default`.
* Each `jdbc-datacollection.d/<name>.xml` becomes the source `<name>`, for example, `postgresql.xml` becomes `postgresql`.
`jdbc-datacollection.d/default.xml` becomes `default.d`, because `default` belongs to `jdbc-datacollection-config.xml`.
* Imported files are moved to `$\{OPENNMS_HOME}/etc_archive/`, with a timestamp appended to the file name.
If a file can't be moved, it is still imported, the log shows a warning, and you have to remove the file from `$\{OPENNMS_HOME}/etc/` yourself.
* A file that does not follow the schema `jdbc-datacollection.xsd`, or that {page-component-title} can't use (for example, a column `type` such as `timeticks` that the collector does not support), is not imported, and the upgrade continues.
* A file in `jdbc-datacollection.d/` whose name does not make a valid source ID is not imported either.
A valid ID starts with a letter or a digit and contains only letters, digits, `.`, `_` and `-`.
* In these cases the log names the file and the error, and the file stays in `$\{OPENNMS_HOME}/etc/`.
Correct or rename the file and upload it on the *Import* tab of the web UI or with the REST API.

IMPORTANT: After the upgrade, {page-component-title} does not read `jdbc-datacollection-config.xml` and the files in `jdbc-datacollection.d/`.
New or changed files in these locations have no effect.

=== XML format

The *Import* tab and *Download XML* use the format of the former `jdbc-datacollection.d/*.xml` files.
This snippet provides a sample collection definition named `opennms-stats` in XML:

[source, xml]
----
<jdbc-collection name="opennms-stats">
  <rrd step="300">
    <rra>RRA:AVERAGE:0.5:1:2016</rra>
    <rra>RRA:AVERAGE:0.5:12:1488</rra>
    <rra>RRA:AVERAGE:0.5:288:366</rra>
    <rra>RRA:MAX:0.5:288:366</rra>
    <rra>RRA:MIN:0.5:288:366</rra>
  </rrd>
  <queries>
    <query name="opennmsQuery" ifType="ignore">
      <statement data-source="opennms">
        <queryString>select count(*) as event_count from events;</queryString>
      </statement>
      <columns>
        <column name="event_count" data-source-name="event_count" alias="event_count" type="GAUGE"/>
      </columns>
    </query>
  </queries>
</jdbc-collection>
----

Once the collection is saved, you can test it using the `collect` command in the xref:reference:karaf-shell/karaf-shell.adoc[Karaf shell]:

[source, console]
----
opennms:collect org.opennms.netmgt.collectd.JdbcCollector 127.0.0.1 collection=opennms-stats data-source=opennms
----

To test this same collection on Minion, you must specify the JDBC settings as service attributes; for example:

[source, console]
----
opennms:collect -l MINION org.opennms.netmgt.collectd.JdbcCollector 127.0.0.1 collection=opennms-stats driver=org.postgresql.Driver url=jdbc:postgresql://localhost:5432/opennms user=opennms password=opennms
----

== Service configuration example

To schedule the collection, add a service to a package in `$\{OPENNMS_HOME}/etc/collectd-configuration.xml` and a matching `collector` entry.
Collectd collects only from IP interfaces that are in the package and have a monitored service with the same name, for example one added through a requisition or a detector.

This example, based on the `PostgreSQL` service in the default configuration, collects the `PostgreSQL` collection from the source `postgresql`:

[source, xml]
----
<service name="PostgreSQL" interval="300000" user-defined="false" status="on">
  <parameter key="collection" value="PostgreSQL"/>
  <parameter key="thresholding-enabled" value="true"/>
  <parameter key="driver" value="org.postgresql.Driver"/>
  <parameter key="user" value="postgres"/>
  <parameter key="password" value="postgres"/>
  <parameter key="url" value="jdbc:postgresql://OPENNMS_JDBC_HOSTNAME:5432/opennms"/>
</service>

<collector service="PostgreSQL" class-name="org.opennms.netmgt.collectd.JdbcCollector"/>
----

The collector replaces `OPENNMS_JDBC_HOSTNAME` in the `url` with the host name that a reverse DNS lookup returns for the interface being collected, or with its IP address if the lookup fails.
To use a data source from `opennms-datasources.xml` instead, set the `data-source` parameter and omit `driver`, `url`, `user` and `password` (not supported on Minion).

The default configuration sets these values with xref:operation:deep-dive/meta-data.adoc[metadata] expressions, such as `${requisition:pg-user|postgres}`, so you can override them per node.
