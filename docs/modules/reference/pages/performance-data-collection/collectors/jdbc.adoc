
= JDBC Collector
:description: Learn how to configure and use the JDBCCollector in OpenNMS {page-component-title} to collect performance data via JDBC drivers.

The JDBCCollector collects performance data via JDBC drivers.
Attributes are retrieved using SQL queries.
The JDBC driver for PostgreSQL is included with {page-component-title}.
Any other JDBC drivers must be manually loaded to collect from other types of database servers (see xref:deployment:core/installing-jdbc-driver.adoc[] and xref:deployment:minion/installing-jdbc-driver.adoc[]).

== Collector facts

[options="autowidth"]
|===
| Class Name            | `org.opennms.netmgt.collectd.JdbcCollector`
| Package               | core
| Supported on Minion   | Yes (see limitations)
| Configuration         | Stored in the database, configuration name `jdbc-datacollection-config` (see <<jdbc-collection-storage>>)
|===

=== Limitations on Minion

No JDBC drivers are included with Minion.
To install a JDBC driver, follow the steps in the xref:deployment:minion/installing-jdbc-driver.adoc[Installation JDBC driver on the Minion] page.

When running on Minion, you also cannot reference the data sources in `opennms-datasources.xml`.
Instead, you must use the service parameters to set the JDBC connection settings.

== JDBC collection configuration

Understanding xref:operation:deep-dive/performance-data-collection/resource-types.adoc#resource-types[resource types] helps when editing collector-specific configuration files.

[[jdbc-collection-storage]]
=== Storage

JDBC collections are stored in the database, as the configuration `jdbc-datacollection-config` of the xref:development:rest/config_management.adoc[Config Management REST API].
This configuration can have several configuration IDs, each with a list of `jdbc-collection` entries.
The collector merges all IDs into one list: `default` first, then the other IDs in alphabetical order.
If a collection name appears more than once, the first one is used and the others are ignored with a warning in the log.

A change takes effect with the next collection; no restart or reload event is needed.
A configuration with a column `type` that {page-component-title} does not support (for example, `timeticks`) is rejected.

To read and change the collections, use the Config Management REST API, for example:

[source, console]
----
curl -u admin:admin https://opennms.example.com/opennms/rest/cm/jdbc-datacollection-config <1>
curl -u admin:admin https://opennms.example.com/opennms/rest/cm/jdbc-datacollection-config/postgresql <2>
curl -X PUT -u admin:admin 'https://opennms.example.com/opennms/rest/cm/jdbc-datacollection-config/postgresql?replace=true' \
     -H 'Content-type: application/json' --data @postgresql.json <3>
curl -X POST -u admin:admin https://opennms.example.com/opennms/rest/cm/jdbc-datacollection-config/my-collections \
     -H 'Content-type: application/json' --data @my-collections.json <4>
----
<1> List the configuration IDs.
<2> Read one configuration as JSON.
<3> Replace a configuration.
<4> Add a configuration with a new ID.

=== Upgrade from XML files

Earlier versions read the collections from `$\{OPENNMS_HOME}/etc/jdbc-datacollection-config.xml` and `$\{OPENNMS_HOME}/etc/jdbc-datacollection.d/*.xml`.
The upgrade imports these files once:

* `jdbc-datacollection-config.xml` becomes the configuration ID `default`.
* Each `jdbc-datacollection.d/<name>.xml` becomes the configuration ID `<name>`, for example, `postgresql.xml` becomes `postgresql`.
`jdbc-datacollection.d/default.xml` becomes `default.d`, because `default` belongs to `jdbc-datacollection-config.xml`.
* Imported files are moved to `$\{OPENNMS_HOME}/etc_archive/`, with a timestamp appended to the file name.
* A file that does not follow the schema `jdbc-datacollection.xsd` is not imported, and the upgrade continues.
* A file in `jdbc-datacollection.d/` whose name does not make a valid configuration ID is not imported either.
A valid ID starts with a letter or a digit and contains only letters, digits, `.`, `_` and `-`.
* In both cases the log names the file and the error, and the file stays in `$\{OPENNMS_HOME}/etc/`.
Correct or rename the file and add it with the REST API.

IMPORTANT: After the upgrade, {page-component-title} does not read `jdbc-datacollection-config.xml` and the files in `jdbc-datacollection.d/`.
New or changed files in these locations have no effect.

=== Collection definition

The XML files and the JSON of the REST API share the same structure.
This snippet provides a sample collection definition named `opennms-stats` in XML:

[source, xml]
----
<jdbc-collection name="opennms-stats">
  <rrd step="300">
    <rra>RRA:AVERAGE:0.5:1:2016</rra>
    <rra>RRA:AVERAGE:0.5:12:1488</rra>
    <rra>RRA:AVERAGE:0.5:288:366</rra>
    <rra>RRA:MAX:0.5:288:366</rra>
    <rra>RRA:MIN:0.5:288:366</rra>
  </rrd>
  <queries>
    <query name="opennmsQuery" ifType="ignore">
      <statement data-source="opennms">
        <queryString>select count(*) as event_count from events;</queryString>
      </statement>
      <columns>
        <column name="event_count" data-source-name="event_count" alias="event_count" type="GAUGE"/>
      </columns>
    </query>
  </queries>
</jdbc-collection>
----

Once the definition is stored, you can test it using the `collect` command in the xref:reference:karaf-shell/karaf-shell.adoc[Karaf shell]:

[source, console]
----
opennms:collect org.opennms.netmgt.collectd.JdbcCollector 127.0.0.1 collection=opennms-stats data-source=opennms
----

To test this same collection on Minion, you must specify the JDBC settings as service attributes; for example:

[source, console]
----
opennms:collect -l MINION org.opennms.netmgt.collectd.JdbcCollector 127.0.0.1 collection=opennms-stats driver=org.postgresql.Driver url=jdbc:postgresql://localhost:5432/opennms user=opennms password=opennms
----

== Service configuration example

To schedule the collection, add a service to a package in `$\{OPENNMS_HOME}/etc/collectd-configuration.xml` and a matching `collector` entry.
Collectd collects only from IP interfaces that are in the package and have a monitored service with the same name, for example one added through a requisition or a detector.

This example, based on the `PostgreSQL` service in the default configuration, collects the `PostgreSQL` collection from the configuration ID `postgresql`:

[source, xml]
----
<service name="PostgreSQL" interval="300000" user-defined="false" status="on">
  <parameter key="collection" value="PostgreSQL"/>
  <parameter key="thresholding-enabled" value="true"/>
  <parameter key="driver" value="org.postgresql.Driver"/>
  <parameter key="user" value="postgres"/>
  <parameter key="password" value="postgres"/>
  <parameter key="url" value="jdbc:postgresql://OPENNMS_JDBC_HOSTNAME:5432/opennms"/>
</service>

<collector service="PostgreSQL" class-name="org.opennms.netmgt.collectd.JdbcCollector"/>
----

The collector replaces `OPENNMS_JDBC_HOSTNAME` in the `url` with the host name that a reverse DNS lookup returns for the interface being collected, or with its IP address if the lookup fails.
To use a data source from `opennms-datasources.xml` instead, set the `data-source` parameter and omit `driver`, `url`, `user` and `password` (not supported on Minion).

The default configuration sets these values with xref:operation:deep-dive/meta-data.adoc[metadata] expressions, such as `${requisition:pg-user|postgres}`, so you can override them per node.
