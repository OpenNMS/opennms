
= Users

WARNING: This API is deprecated in {page-component-title} 37 and will be removed in {page-component-title} 38.
Use the xref:development:rest/users_v2.adoc[Users (v2)] API at `/api/v2/users` instead.

Users are stored in the database.
You cannot use hibernate criteria for filtering.
The write operations need the `ROLE_ADMIN` role, like the v2 API, and answer `403` without it.
They use the same checks as the v2 API:

* A new user ID must not be reserved or look like `admin` or `rtc`, and must not contain markup, whitespace, control characters or any of `: / \ % ? #`.
  The response is `400`.
* Comments must not contain markup, and every value must fit its column.
  Duty schedules are validated, and every role must be a known security role.
  Values that are already stored are accepted unchanged.
  The response is `400`.
* A password is only accepted in plain text with `hashPassword=true`, and is always stored hashed and salted.
  A password hash is not accepted, and `passwordSalt` is ignored.
  A missing or blank password, or one without `hashPassword=true`, is refused.
  While `org.opennms.users.allowUnsalted` is `false`, a user whose stored password is unsalted cannot be changed until it gets a new password.
  The response is `400`.
* A form `PUT` accepts only the keys `fullName`, `comments`, `email`, `password`, `hashPassword`, `dutySchedule` and `roles`, spelled exactly.
  Any other key is refused before anything is changed.
  The response is `400`.
  For `username` or `name`, in any case, it points to `PUT /api/v2/users/\{userId}/rename`.
* A `POST` without `user-id` is refused.
  The response is `400`.
* The `admin` and `rtc` users cannot be deleted, and `admin` keeps `ROLE_ADMIN`.
  The response is `400`.
* The last holder of `ROLE_ADMIN` cannot be deleted or lose the role, and a user who supervises an on-call role or is the target of a notification destination path cannot be deleted.
  A path target can be deleted when a group or an on-call role has the same name, because the path notifies that group or role.
  The response is `409`.
* A write answers `409` when another request changed any user while it ran, not only the same one.
  Nothing was saved, and the request can be sent again.
* A caller without `ROLE_ADMIN` sees `xxxxxxxx` in place of the password hash of every user but their own.

`GET /users/whoami` is deprecated too.
Use `GET /rest/whoami`, which returns a different shape.

== GETs (reading data)

[caption=]
.Users API GET functions
[options="autowidth"]
|===
| Parameter | Description

| /users
| Get a list of users.

| /users/\{username}
| Get a specific user, by username.

| /users/whoami
| Get the authenticated user, without the password fields.
Use `GET /rest/whoami` instead.
|===

== POST (adding data)

POST requires XML using `application/xml` as its `Content-Type`.

[caption=]
.Users API POST function
[cols="1,3"]
|===
| Parameter | Description

| /users?hashPassword=true
| Add a user, or overwrite the user with the same `user-id`.
The `password` is the password in plain text: it is hashed and salted when it is saved.
A password hash is not accepted. +
An overwrite may send the stored `password` and `passwordSalt` back unchanged, as `GET` returns them, without `hashPassword=true`: the stored password is kept. +
The stored hash sent back with `hashPassword=true` is refused (`400`): it would be hashed again.
|===

== PUTs (modifying data)

[caption=]
.Users API PUT functions
[cols="1,3"]
|===
| Parameter | Description

| /users/\{username}
| Update an existing user with form fields: `fullName`, `comments`, `email`, `password`, `dutySchedule` and `roles`. +
A `password` is the new password in plain text, and needs the field `hashPassword=true`: it is hashed and salted when it is saved.

| /users/\{username}/roles/\{rolename}
| Add a security role to the user.
|===

== DELETEs (removing data)

[caption=]
.Users API DELETE functions
[options="autowidth"]
|===
| Resource  | Description

| /users/\{username}
| Delete a user.

| /users/\{username}/roles/\{rolename}
| Remove a security role from the user.
|===

See also the database-backed xref:development:rest/users_v2.adoc[Users (v2)] API.
