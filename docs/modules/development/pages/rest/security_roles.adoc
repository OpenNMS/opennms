= Security Roles

Security roles control what a user may do in OpenNMS, for example `ROLE_ADMIN` or `ROLE_USER`.
This REST API, served at `/api/v2/security-roles`, lists the built-in roles and manages custom ones.
Roles are assigned to users with the xref:development:rest/users_v2.adoc[Users (v2)] API.

== Store mode

This API works only when users and groups are stored in the database (`org.opennms.usermgmt.store=db`).
When the store is `xml`, every operation returns `503 Service Unavailable` with the text `User management through this API needs org.opennms.usermgmt.store=db.`

== Permissions

Every operation, including reads, requires the `ROLE_ADMIN` role.
Other users receive `403 Forbidden`.

All operations produce and consume JSON.
Error responses carry a plain-text message.

== Status codes

[caption=]
[cols="1,4"]
|===
| Code | Meaning

| 400 | Validation failed, for example a missing or unknown field value, a name in the wrong format, or a protected object.
| 403 | The caller does not hold `ROLE_ADMIN`.
| 404 | The named object does not exist.
| 409 | The object already exists, another object still refers to it, or the data was changed at the same time by another request (try again).
| 412 | `If-Match` was sent and no longer matches the object.
| 503 | The user-management store is `xml`.
|===

== GETs (reading data)

[caption=]
.Security Roles API GET functions
[cols="40%,60%"]
|===
| Resource | Description

| /security-roles
| Get every role: built-in roles first, then custom roles, each sorted by name.
Each role carries `userCount`, the number of users that hold it.

| /security-roles/\{name}
| Get one role. The response carries an `ETag` header and no `userCount`; use the list for the count.
|===

== POSTs (adding data)

[caption=]
.Security Roles API POST functions
[cols="40%,60%"]
|===
| Resource | Description

| /security-roles
| Create a custom role.
The name is upper-cased, gets the `ROLE_` prefix when it lacks one, and may contain only `A-Z`, `0-9` and `_`.
Returns `201 Created` with the role and its `ETag`, or `409` when it already exists.
|===

== PUTs (modifying data)

[caption=]
.Security Roles API PUT functions
[cols="40%,60%"]
|===
| Resource | Description

| /security-roles/\{name}
| Update the description of a custom role.
An omitted `description` is preserved and an empty one clears it.
Returns `200` with the role and its `ETag`.
|===

Roles cannot be renamed.
The description of a built-in role is read-only, so a PUT to one returns `400`.

== DELETEs (removing data)

[caption=]
.Security Roles API DELETE functions
[cols="40%,60%"]
|===
| Resource | Description

| /security-roles/\{name}
| Delete a custom role.
Returns `204 No Content`.
Built-in roles cannot be deleted (`400`).
A role that users still hold returns `409`; the message lists those users.
|===

== Detecting concurrent edits

Every GET of a single role returns an `ETag` header: the quoted version of the role, for example `"4817"`.
The version is an opaque number: it changes on every change of the role's own fields, and a version is never reused, not even by a role that is deleted and created again under the same name.
Granting the role to a user or revoking it is a change of the user, not of the role, so it does not change the role's version.
Do not interpret it, count with it or compare it for order, only send it back.
`PUT` and `DELETE` accept an `If-Match` header carrying that tag.

`If-Match` is optional: a write without it always goes through.
`*` matches any existing role.
The tag may be weak (`W/"4817"`), and the header may list several tags separated by commas: the request goes through if any of them is the current one.
If no tag is the current one, or the header is not a list of entity tags, the request fails with `412 Precondition Failed` and nothing is changed.
If the role does not exist, a request with an `If-Match` header (even `*`) also fails with `412`; without the header it is `404 Not Found`.
`If-None-Match` is ignored.
Every successful write returns the new `ETag`.

The `version` field in a JSON body is informational.
It is ignored when you send it: a write without `If-Match` goes through even if the body holds an old version.
To detect concurrent edits, send the version in `If-Match`.

== Role fields

[caption=]
[cols="1,3"]
|===
| Field | Description

| name | Role name, such as `ROLE_AUDITOR`. Required on create.
| description | Description. Only writable on custom roles.
| builtin | `true` for a built-in role. Read-only.
| userCount | Number of users that hold the role. Only in the list; read-only.
| version | Opaque row version, also sent as the `ETag`. Ignored on input.
|===

== Examples using cURL

[source,bash]
----
curl -u admin:admin -X POST -H 'Content-Type: application/json' \
  -d '{"name": "auditor", "description": "Read-only auditing"}' \
  http://localhost:8980/opennms/api/v2/security-roles

curl -u admin:admin http://localhost:8980/opennms/api/v2/security-roles

curl -u admin:admin -X PUT -H 'Content-Type: application/json' -H 'If-Match: "4817"' \
  -d '{"description": "Audit access"}' http://localhost:8980/opennms/api/v2/security-roles/ROLE_AUDITOR

curl -u admin:admin -X DELETE http://localhost:8980/opennms/api/v2/security-roles/ROLE_AUDITOR
----
