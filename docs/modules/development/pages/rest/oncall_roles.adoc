= On-Call Roles

An on-call role names a membership group, a supervisor and a set of schedules that say which users are on call, and when.
This REST API is served at `/api/v2/oncall-roles`.

== Store mode

This API works only when users and groups are stored in the database (`org.opennms.usermgmt.store=db`).
When the store is `xml`, every operation returns `503 Service Unavailable` with the text `User management through this API needs org.opennms.usermgmt.store=db.`

== Permissions

Every operation, including reads, requires the `ROLE_ADMIN` role.
Other users receive `403 Forbidden`.

All operations produce and consume JSON.
Error responses carry a plain-text message.

== Status codes

[caption=]
[cols="1,4"]
|===
| Code | Meaning

| 400 | Validation failed, for example a missing or unknown field value, a name in the wrong format, or a protected object.
| 403 | The caller does not hold `ROLE_ADMIN`.
| 404 | The named object does not exist.
| 409 | The object already exists, another object still refers to it, or the data was changed at the same time by another request (try again).
| 412 | `If-Match` was sent and no longer matches the object.
| 503 | The user-management store is `xml`.
|===

== GETs (reading data)

[caption=]
.On-Call Roles API GET functions
[cols="40%,60%"]
|===
| Resource | Description

| /oncall-roles
| Get every role with its schedules, sorted by name and ignoring case.
The response has no `ETag` header.
Each item carries its `version`, but a `PUT` or `DELETE` takes the tag from a GET of the single role.

| /oncall-roles/\{name}
| Get one role. The response carries an `ETag` header.
|===

== POSTs (adding data)

[caption=]
.On-Call Roles API POST functions
[cols="40%,60%"]
|===
| Resource | Description

| /oncall-roles
| Create a role.
`name`, `membershipGroup` and `supervisor` are required, and the group and supervisor must exist.
Returns `201 Created` with the role and its `ETag`, or `409` when it already exists.

| /oncall-roles/\{name}/rename
| Rename a role in place. The body is `{"newName": "NewName"}`.
Returns `200` with the role and its `ETag`, `400` when the new name is the current name, or `409` when the new name is taken.
|===

WARNING: A rename does not update `destinationPaths.xml`.
Destination paths that name the old role keep pointing at it, so update them yourself.

A role name starts with a letter or a digit and contains only letters (of any script), digits, the characters `_`, `-`, `.`, `(` and `)`, and single spaces between words.
It is limited to 256 characters.
Names already stored are not re-checked.

== PUTs (modifying data)

[caption=]
.On-Call Roles API PUT functions
[cols="40%,60%"]
|===
| Resource | Description

| /oncall-roles/\{name}
| Update a role.
Returns `200` with the role and its `ETag`.
|===

In a PUT body, a field that is omitted is left as it is and `description` set to an empty string is cleared.
An omitted `schedules` keeps the stored schedules, and a present `schedules`, including `[]`, replaces them.

A PUT that changes `membershipGroup` checks every schedule against the new group, also the stored ones that are kept or sent back unchanged.
If a schedule names a user who is not a member of the new group, the request returns `400` naming those users, and nothing is changed.
To change the group, send `schedules` without the schedules of those users in the same request.

== DELETEs (removing data)

[caption=]
.On-Call Roles API DELETE functions
[cols="40%,60%"]
|===
| Resource | Description

| /oncall-roles/\{name}
| Delete a role. Returns `204 No Content`.
Returns `409` while a destination path in `destinationPaths.xml` names the role, as a target or in an escalation; the message names the paths.
A path does not count when a group has the same name, because notifd sends to that group instead.
|===
== Detecting concurrent edits

Every GET of a single role returns an `ETag` header: the quoted version of the role, for example `"4817"`.
The version is an opaque number: it changes on every change of the role, including a change of what it contains, and a version is never reused, not even by a role that is deleted and created again under the same name.
Do not interpret it, count with it or compare it for order, only send it back.
`PUT`, `POST …/rename` and `DELETE` accept an `If-Match` header carrying that tag.

`If-Match` is optional: a write without it always goes through.
`*` matches any existing role.
The tag may be weak (`W/"4817"`), and the header may list several tags separated by commas: the request goes through if any of them is the current one.
If no tag is the current one, or the header is not a list of entity tags, the request fails with `412 Precondition Failed` and nothing is changed.
If the role does not exist, a request with an `If-Match` header (even `*`) also fails with `412`; without the header it is `404 Not Found`.
`If-None-Match` is ignored.
Every successful write returns the new `ETag`.

The `version` field in a JSON body is informational.
It is ignored when you send it: a write without `If-Match` goes through even if the body holds an old version.
To detect concurrent edits, send the version in `If-Match`.

== Role fields

[caption=]
[cols="1,3"]
|===
| Field | Description

| name | Role name. Required on create.
| description | Description, at most 4096 characters. See <<oncall-description>>.
| membershipGroup | Name of an existing group. Required on create. A new schedule must name a user who is a member of this group; schedules already stored are not re-checked (see <<stored-schedules>>), unless the request changes the group.
| supervisor | User id of an existing user. Required on create.
| schedules | List of schedules (see below).
| version | Opaque row version, also sent as the `ETag`. Ignored on input.
|===

== Schedule fields

Each schedule has a `user` (an existing user), a `type` and a list of `times`.
A schedule needs at least one time.

[caption=]
[cols="1,3"]
|===
| Field | Description

| user | User id the schedule applies to.
| type | One of `specific`, `daily`, `weekly` or `monthly`.
| times | List of times, each with `id`, `day`, `begins` and `ends`. `id` is optional.
|===

The format of `day`, `begins` and `ends` depends on the schedule type.
`begins` must be strictly before `ends`.

The month abbreviation in the `specific` times is parsed in the default locale of the OpenNMS server, exactly as notifd parses it.
On a server with an English locale the months are `Jan`, `Feb`, `Mar`, `Oct` and so on; on a server with another locale they are that locale's abbreviations.

A `specific` time is also read in the server's time zone, and a time that the time zone skips is rejected.
For example, on a server in `America/New_York`, `08-Mar-2026 02:30:00` does not exist, because the clocks go from 02:00 to 03:00 that day.

[caption=]
[cols="1,2,3"]
|===
| Type | `day` | `begins` and `ends`

| specific | Not allowed. | `dd-MMM-yyyy HH:mm:ss`, for example `21-Oct-2026 08:00:00` on a server with an English locale.
| daily | Not allowed. | `HH:mm:ss`, for example `08:00:00`.
| weekly | A day name, `sunday` to `saturday`. | `HH:mm:ss`.
| monthly | A day of the month, `1` to `31`. | `HH:mm:ss`.
|===

[[oncall-description]]
== Description

The description is at most 4096 characters long, counted after leading and trailing whitespace is removed.
A longer description returns `400`.
A stored description that is longer stays valid while a `PUT` sends it back unchanged, apart from surrounding whitespace.

[[stored-schedules]]
== Stored schedules

A schedule that is already stored is exempt from the membership check, but only as a whole entry.
If you send it back unchanged, it is kept.
If you change any part of it, for example you shorten a time, the changed entry counts as new and must pass the membership check.

This matters for a user who has left the membership group.
You cannot change the stored schedule of that user: you can only keep it unchanged or remove it.
To change it, add the user to the membership group again first.

The exemption ends when a request changes the membership group: then every schedule must name a member of the new group.

== Examples using cURL

[source,bash]
----
curl -u admin:admin -X POST -H 'Content-Type: application/json' -d '{
  "name": "NightShift", "description": "Night on-call",
  "membershipGroup": "Ops", "supervisor": "admin",
  "schedules": [{"user": "jdoe", "type": "weekly",
    "times": [{"day": "monday", "begins": "18:00:00", "ends": "23:59:59"}]}]
}' http://localhost:8980/opennms/api/v2/oncall-roles

curl -u admin:admin -i http://localhost:8980/opennms/api/v2/oncall-roles/NightShift
# ... ETag: "4830" ...

# Change the description only; the schedules are kept
curl -u admin:admin -X PUT -H 'Content-Type: application/json' -H 'If-Match: "4830"' \
  -d '{"description": "Overnight"}' http://localhost:8980/opennms/api/v2/oncall-roles/NightShift

curl -u admin:admin -X POST -H 'Content-Type: application/json' \
  -d '{"newName": "Overnight"}' http://localhost:8980/opennms/api/v2/oncall-roles/NightShift/rename
curl -u admin:admin -X DELETE http://localhost:8980/opennms/api/v2/oncall-roles/Overnight
----
