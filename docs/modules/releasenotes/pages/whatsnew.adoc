= What's New in OpenNMS {page-component-title} 37

== System requirements and Dependencies

* Java 21: OpenNMS {page-component-title} requires JDK 21.
* PostgreSQL 14 or higher: This version of OpenNMS {page-component-title} requires a supported version of PostgreSQL.

== New features and important changes

=== Spring, Hibernate, and Camel platform upgrade
The core application frameworks have been upgraded to currently supported versions:
Spring Framework 5.3, Spring Security 5.8, Hibernate 5.6, Hibernate Validator 6.2, and Apache Camel 3.22.
The OpenNMS-patched forks of Spring, Spring Security, and Hibernate have been removed in favor of stock releases,
and Eclipse Gemini Blueprint has been replaced by an OpenNMS Spring OSGi extender.

Most installations require no action, but there are behavior and compatibility changes for installations with
custom Spring Security configuration (SSO, LDAP), custom Camel routes, or plugins that use the OpenNMS persistence APIs.
See xref:spring-hibernate-upgrade.adoc[Spring, Hibernate, and Camel Platform Upgrade] for details.

=== Faster IP address filtering (IPLIKE)

Filter expressions that use IPLIKE are now translated to native PostgreSQL `inet` comparisons where possible, and new expression indexes on the `ipinterface`, `events`, `alarms`, and `notifications` tables let the database answer them without scanning every row.
This primarily benefits large environments: filter evaluation and event searches by IP address that previously took seconds to minutes generally complete in milliseconds.

Expressions that cannot be translated (for example, patterns that contain an IPv6 zone identifier, or that expand to many separate address ranges, such as `*.*.*.1`) continue to use the `iplike` stored procedure.
The bundled PL/pgSQL implementation of `iplike` has been reworked for speed and is installed automatically during the upgrade; installs that use the optional compiled iplike extension keep it, but it is no longer needed.
On installs that use the compiled extension, translated expressions follow the PL/pgSQL implementation's semantics; the one visible difference is the match-all patterns (`*.*.*.*` and `*:*:*:*:*:*:*:*`), which now match every non-null address regardless of address family, as they always have under the PL/pgSQL implementation.
Hexadecimal digits in IPv6 addresses and patterns now match regardless of case; previously, addresses stored with uppercase digits never matched.
The upgrade builds the new indexes, which can take several minutes on an `events` table with tens of millions of rows that have an IP address.
If necessary, set the system property `org.opennms.iplike.native=false` to restore the previous query behavior.

=== Trap audit log
Trapd on core and Minion can now write one line per received SNMP trap, with the sender address and trap OID, to a dedicated `trap-audit.log`.
It is disabled by default and is enabled by setting the `trap-audit` logger to `INFO` in `etc/log4j2.xml` (core) or `etc/org.ops4j.pax.logging.cfg` (Minion).
See xref:reference:daemons/daemon-config-files/trapd.adoc#trap-audit-log[Trap audit log].

=== Legacy navigation bar removed
The legacy FreeMarker navigation bar and the `?oldmenu=true` switch that selected it have been removed.

* `maps.htm` and `dashboards.htm` now return 404; the Maps and Dashboards entries of the side menu replace them.
* If you edited `${OPENNMS_HOME}/jetty-webapps/opennms/WEB-INF/dispatcher-servlet.xml` and kept your copy during the upgrade (Debian/Ubuntu packages ask about it), or supply one through the container's `/opt/opennms-jetty-webinf-overlay`, re-apply your changes to the new file: the old one refers to classes that have been removed, and the web UI does not start with it.
* `menu-template-default.json` is the default menu shipped with the product, identical to the stock `menu-template.json`; do not edit it.
* Admin-only entries now carry `roles` in `menu-template.json`.
* Package upgrades replace `menu-template.json`, so a customized copy is lost: back it up before upgrading and re-apply your changes to the new file. A copy supplied through the container's `/opt/opennms-jetty-webinf-overlay` is kept; compare it with `menu-template-default.json` to pick up the new `roles`.
* `locationMatch` in menu templates is ignored.
* The "Action" results of the central search ("Open ...") now come from `menu-template.json` and follow the same `roles` as the menu.
* The search "Open ..." results are cached per user for up to 5 minutes. They pick up edits to the menu template, and a user's changed roles (which take effect at the user's next login), within that time. The side menu picks up both on the next page load.
* Pages displayed inside an iframe, both legacy JSP pages and the `ui/` app, no longer show the menu, and pressing Escape does not bring it back. To keep the menu in a frame, put `-with-header` in the frame's name, for example `<iframe name="noc-with-header" src="...">`. See xref:operation:deep-dive/admin/configuration/http-security-headers.adoc[HTTP Security Headers].

=== Trends removed
The Trends page has been removed from the Dashboards menu and from the product. `etc/trend-configuration.xml` is no longer read and can be deleted.

=== Charts removed
The Charts page, its JFreeChart rendering and the `features/charts` module have been removed from the Dashboards menu and from the product. `etc/chart-configuration.xml` and its configuration model go with it; the file is no longer read.

=== Heatmap removed
The Heatmap page has been removed from the Dashboards menu and from the product, together with the `/rest/heatmap` endpoint and the `org.opennms.heatmap.*` system properties, which are no longer read.
The `getHeatMapItemsForEntity` methods are gone from the internal `AlarmDao` and `OutageDao` interfaces; they were not part of the Integration API.
A `org.opennms.web.console.centerUrl` that still names the heatmap or trend box is skipped when the legacy home page renders.

=== AMQP integration removed
The AMQP event forwarder, event receiver and alarm northbounder (`opennms-amqp-*` Karaf features) have been removed, together with their `org.opennms.features.amqp.*` configuration PIDs, the `opennms-camel-amqp` feature and the Qpid JMS client.
Before upgrading, remove `opennms-amqp-event-forwarder`, `opennms-amqp-event-receiver` and `opennms-amqp-alarm-northbounder` from `featuresBoot` in `etc/org.apache.karaf.features.cfg` and from any file under `etc/featuresBoot.d/`.
A stale entry in `featuresBoot` is skipped at startup, but a stale entry in a `featuresBoot.d` file stops every feature listed in that directory from being installed.
The `etc/org.opennms.features.amqp.eventforwarder.cfg`, `etc/org.opennms.features.amqp.eventreceiver.cfg` and `etc/org.opennms.features.amqp.alarmnorthbounder.cfg` files are no longer used and can be deleted.

=== Statsd removed
The Metrics Statistics (statsd) page and the Statsd daemon have been removed, together with `etc/statsd-configuration.xml` and the `CORE_SERVICE_STATSD_ENABLED` variable.
A Statsd entry left in an existing `etc/service-configuration.xml` is ignored with a warning at startup and can be deleted, as can `etc/statsd-configuration.xml`.
The "TOP 20 nodes by I/O Wait" database report and the response-time offenders section of the Response Time Summary report, which only Statsd could feed, are removed as well.
Existing rows in the `statisticsreport` tables are left in place and continue to be purged by Vacuumd.

=== SNMP datacollection config moved to DB with new UI
The contents of `etc/datacollection-config.xml` and `etc/datacollection/\*.xml` are migrated into the database during the upgrade process, and the original files are moved to `etc_archive/`.
After upgrade, manage SNMP data collection through the *Administration -> Manage SNMP Data Collection Config* page (or the REST API under `/api/v2/datacollectionconf`).
Direct edits to the archived XML files no longer take effect.

=== SNMP MIB compiler: new UI and REST API
The SNMP MIB compiler has a new UI and a REST API under `/api/v2/mibs`.
Use the *Tools -> SNMP MIB Compiler* page to upload, view, edit, compile, and delete MIB files.
From a compiled MIB, you can generate event definitions, an SNMP data collection group, and graph templates.
Generated event definitions and data collection groups are stored in the database, the same as manual uploads on the event configuration and SNMP data collection pages.
When you generate event definitions, the page warns about UEIs that other event sources already define.
Before it saves the events, it shows which existing definitions the new ones replace and asks you to confirm.
A new event source is evaluated before all existing sources.
The generated definitions do not contain alarm data, so unless you add it before the save, traps that an existing definition turned into alarms no longer create or clear alarms.
Graph templates are written to `etc/snmp-graph.properties.d/`.

The legacy Vaadin MIB compiler (`admin/mibCompiler.jsp`) has been removed, together with the `vaadin-snmp-events-and-metrics` Karaf feature.
That feature also held the unlinked Vaadin event and SNMP collection editors (`admin/manageEvents.jsp`, `admin/manageSnmpCollections.jsp`), which edited XML files that now live in the database.
Use the *Manage Event Configurations* and *Manage SNMP Data Collection Config* pages instead.
Before upgrading, remove `vaadin-snmp-events-and-metrics` from the Karaf boot features:

* In `featuresBoot` in `etc/org.apache.karaf.features.cfg`, a stale entry is skipped at startup, but remove it to keep the file current.
* In a file under `etc/featuresBoot.d/`, a stale entry stops every feature listed in that directory from being installed, for example plugins and the Kafka producer.
{page-component-title} still starts, but the Karaf extender health check reports a failure, and `karaf.log` contains `No matching features for vaadin-snmp-events-and-metrics/0.0.0`.

=== Snmp Config file `snmp-config.xml` moved to DB with new UI
The contents of `snmp-config.xml` are migrated into the database during the upgrade process,
and the original file is moved to `etc_archive/`.

After upgrade, manage SNMP configuration through the *Integrations -> SNMP Agent Configuration* page
(or the REST v2 API under `/api/v2/snmp-config`). Direct edits to the archived XML file no longer take effect.

The new UI supports definition lookup by IP address and location, profile management, and supports both IPv4 and IPv6.

The legacy file-based SNMP credential encryption feature (the `org.opennms.snmp.encryption.enabled` property
and the `snmp-config-encrypt` / `snmp-config-decrypt` Karaf commands) has been removed.
The upgrade handles existing encrypted configurations automatically.
For protecting SNMP credentials, use Secure Credentials Vault (SCV) metadata expressions in your SNMP configuration.

See xref:development:rest/snmp_configuration.adoc[SNMP Configuration REST API] for details.

=== Trapd Config file `trapd-configuration.xml` moved to DB with new UI
The contents of `trapd-configuration.xml` are migrated into the database during the upgrade process,
and the original file is moved to `etc_archive/`.

After upgrade, manage trapd configuration through the *Integrations -> Trap Configuration* page
(or the REST v2 API under `/api/v2/trapd`). Direct edits to the archived XML file no longer take effect.

See xref:development:rest/trapd-rest-api.adoc[Trapd REST API (v2)] for details.

=== Threshold configuration moved to DB with new UI
The contents of `thresholds.xml` and `threshd-configuration.xml` are migrated into the database during the
upgrade process, and the original files are moved to `etc_archive/`.

After upgrade, manage thresholds through the *Administration -> Configure Thresholds* page (or the REST v2
API under `/api/v2/thresholding` and `/api/v2/threshd`). Direct edits to the archived XML files no longer
take effect.

The page also covers threshd packages and services, which previously had no UI at all, and adds creating,
renaming and deleting threshold groups, which previously required editing the XML by hand.

The legacy JSP threshold editor at `admin/thresholds/index.htm` has been removed. Update any bookmarks or
external links to `ui/index.html#/threshold-config`.

See xref:development:rest/thresholds-rest-api.adoc[Thresholds REST API (v2)] for details.

=== Environment variable support in service configuration
Individual services in `service-configuration.xml` can now be enabled or disabled at runtime via environment variables,
using the pattern `CORE_SERVICE_<NAME>_ENABLED`. For example, set `CORE_SERVICE_TELEMETRYD_ENABLED=false`
to disable Telemetryd without editing the configuration file.

This is particularly useful for containerized deployments where service composition is controlled via environment.
Existing `enabled="true|false"` values in the file remain the default when no environment variable is set.

NOTE: The `Manager` and `Eventd` services must always be enabled and cannot be disabled via environment variable.

=== Ticketing plugin is now automatic

The `OSGiBasedTicketerPlugin` is now the default ticketer plugin.
Ticketing is automatically enabled when an OSGi-based ticketer plugin is installed and disabled when it is removed.
The `NullTicketerPlugin` and the `opennms.ticketer.plugin` property have been removed.

IMPORTANT: Remove any `opennms.ticketer.plugin` line from `etc/opennms.properties` and `etc/opennms.properties.d/` before upgrading.
Older releases, including the Docker stock config, shipped `opennms.ticketer.plugin=org.opennms.netmgt.ticketd.NullTicketerPlugin` by default, so it's likely present even if you never touched your config -- leaving it in causes a `ClassNotFoundException` on startup.
An `opennms.ticketer.plugin=...OSGiBasedTicketerPlugin` entry is also now redundant and can be removed.
The `opennms.alarmTroubleTicketEnabled` property is no longer required but can still be used to explicitly enable or disable ticketing.

=== MCP server for AI agents
{page-component-title} can now be accessed by AI agents through the https://modelcontextprotocol.io[Model Context Protocol] (MCP): installing the optional `opennms-mcp-server` feature exposes tools to query nodes and alarms, acknowledge or clear alarms, and send events, governed by the user's existing roles.
See xref:development:oia/mcp-server.adoc[MCP Server] for installation and details.

=== Light and dark mode for the Vue UI
The Vue-based web UI now supports a light/dark theme toggle, in addition to the system-default option.

=== File `eventconf.xml` moved to DB
The contents of the file `eventconf.xml` will be stored in the database during the upgrade process and all files in `etc/events` will be moved to `etc_archive`.
These events will not be imported into the database.

After upgrade, manage event configurations through the *Administration -> Manage Event Configurations* page
(or the REST API under `/api/v2/eventconf`).

See xref:operation:deep-dive/events/event-configuration.adoc#migrating-event-files-after-upgrade[Migrating event files after upgrade] for the steps to re-upload your customized event files from `etc_archive/events/`.

=== ActiveMQ store and JVM temp directory moved out of the Karaf cache
`java.io.tmpdir` moved from `$\{OPENNMS_HOME}/data/tmp` to `$\{OPENNMS_HOME}/tmp`, and the embedded ActiveMQ broker's on-disk store (`activemq.data`) moved from `$\{OPENNMS_HOME}/data/tmp/activemq` to `$\{OPENNMS_HOME}/var/activemq`.

To keep the previous behavior, see xref:operation:deep-dive/admin/configuration/startup.adoc[Startup Configuration], or xref:reference:configuration/core-docker.adoc[Core Docker] for container deployments.

=== WSMan WinRS support, WsManShellMonitor, and WsManShellDetector
The OpenNMS WSMan library has added support for WinRS remote shell commands.
A corresponding monitor and detector have been added to leverage these new capabilities.

=== WSMan Kerberos message encryption
The OpenNMS WSMan library has added support for Kerberos message encryption over unencrypted channels.
The existing configuration has been extended to take advantage of this new feature.
This should greatly reduce friction when deploying WS-Man / WinRM-based monitoring on Windows.

=== Custom Performance Graphs preview
A preview interface has been added to eventually replace the previous Ad-Hoc Graphing workflow with a more modern UI that takes advantage of current OpenNMS REST APIs for nodes, resources, and metric measurements.

=== Notifd modernization
The `notifd` daemon has had much of its underlying software infrastructure modernized, including mail libraries, to improve support for modern protocols.

=== Kafka producer JSON payloads for metrics
The Kafka producer feature now supports producing metric payloads to Kafka as JSON format.

=== OpenAPI docs improvements
There are extensive improvements to how our OpenAPI docs are generated and rendered.
This includes more reliable rendering with reduced load times as well as expected payloads and responses for many more API endpoints.

=== Karaf shell pubkey auth
Support has been added for configuring Karaf shell authentication using ssh public keys.

=== Poll and collection timing metrics
Pollerd and Collectd now publish timers over JMX, both overall and per service name, under `org.opennms.netmgt.poller:name=polls*` and `org.opennms.netmgt.collectd:name=collections*`.
They report average, minimum, and maximum poll and collection times along with polls and collections per second.
The overall timers combine every service, so the per-service timers are generally more useful for timing.
Failed polls and collections are timed as well, often at their full timeout including retries, and poll times include any Minion queueing, so a few unreachable nodes can raise a service's average.
The average, minimum, and maximum are weighted toward recent values, but a single slow poll can remain the maximum for up to about half a day.
OpenNMS collects them about itself and graphs them under the *Pollerd Poll Stats* and *Collectd Collection Stats* resources.

== Breaking changes

=== Kafka SASL/OAUTHBEARER endpoint URLs are blocked by default
The Kafka client libraries have been upgraded to 3.9.1, which adds the `org.apache.kafka.sasl.oauthbearer.allowed.urls` system property for CVE-2025-27817.
Core, Minion, and Sentinel now ship that property with an empty value in `etc/opennms.properties` and `etc/system.properties`, so the client contacts no token or JWKS endpoint URL.
If you authenticate to Kafka with SASL/OAUTHBEARER, set the property to a comma-separated list of your endpoint URLs before upgrading.
Other SASL mechanisms, such as SCRAM, are not affected.
See xref:deployment:core/message-broker/kafka.adoc[Kafka message broker] for the client configuration.

=== Jakarta Mail migration and OAuth2 (XOAUTH2) SMTP support
All mail sending and reading now uses Jakarta Mail 2.1 (Eclipse Angus) instead of JavaMail 1.4; existing `javamail-configuration.xml` and `javamail-configuration.properties` files load unchanged.
The JMTA local-MTA transport is gone (`use-jmta` is still accepted, but mail is sent over SMTP to the configured mail host), `<javamail-property>` entries now reach the mail session instead of being ignored, and SSL/TLS connections now verify that the server certificate covers the mail host.
See xref:operation:deep-dive/notifications/configuration.adoc#mail-tls[Mail server TLS] for the TLS properties, and xref:operation:deep-dive/admin/configuration/token-authentication.adoc[token authentication] for the OAuth2 (XOAUTH2) SMTP authentication that Microsoft 365 and Gmail now require.

=== Scripted (BSF) notifications now run on JSR-223
`BSFNotificationStrategy` executes scripts through the Java scripting API instead of the retired Apache Bean Scripting Framework; existing scripts generally keep working, but see xref:operation:deep-dive/notifications/strategies/scripting.adoc[Scripted Notifications] for the deprecated parameters and behavior changes.

=== Slack and Mattermost notification strategies replaced by a webhook strategy
`SlackNotificationStrategy` and `MattermostNotificationStrategy` have been removed in favor of `WebhookNotificationStrategy`, which takes the URL, method, headers, and body from the notification command and so can also target Microsoft Teams, Discord, and non-chat endpoints.
The `org.opennms.netmgt.notifd.slack.*` and `org.opennms.netmgt.notifd.mattermost.*` properties no longer have any effect.

Neither strategy shipped as a stock notification command, so this affects only hand-added commands, which fail when a notice is sent until their `<execute>` element and arguments are updated.
See xref:operation:deep-dive/notifications/strategies/webhook.adoc#migrating-from-slack-and-mattermost[Webhook Notifications] for the mapping.

=== XMPP (Jabber) notification strategies removed
The XMPP notification strategies have been removed and `xmpp-configuration.properties` is ignored.
Existing `users.xml` files with `xmppAddress` contacts still load, but no notifications are sent to them.

=== PercDetector removed
The PercDetector has been removed.
Remove any detector that uses the class `org.opennms.netmgt.provision.detector.snmp.PercDetector` from your foreign source definitions before upgrading.
The xref:reference:service-assurance/monitors/PercMonitor.adoc[PercMonitor] is unchanged; to keep monitoring a PERC array, add the PERC service to nodes in their requisitions, or detect it with an xref:reference:provisioning/detectors/SnmpDetector.adoc[SnmpDetector] on the OID `.1.3.6.1.4.1.3582.1.1.2.1.3.0.0`.

An `ircCat` command left in an existing `notificationCommands.xml` still loads, but notices routed to it fail when sent.

=== OpenManageChassisDetector removed
The OpenManageChassisDetector has been removed.

=== OmsaStorageDetector removed
The OmsaStorageDetector has been removed.

=== SAML and OpenID SSO support removed
Spring Security 5.8 has no compatible SAML/OpenID extension libraries, so they are no longer shipped.
If single sign-on is enabled through a custom `spring-security.d/*.xml` file, the web application fails to start after the upgrade — this affects *all* logins, not just SSO.
See xref:spring-hibernate-upgrade.adoc#spring-hibernate-upgrade[Spring, Hibernate, and Camel Platform Upgrade] for this and other upgrade-related compatibility changes.

=== MSExchangeDetector removed
The MSExchangeDetector has been removed.
Remove any detector that uses the class `org.opennms.netmgt.provision.detector.msexchange.MSExchangeDetector` from your foreign source definitions before upgrading.
Use the xref:reference:provisioning/detectors/WsmanWqlDetector.adoc[WsmanWqlDetector] or the xref:reference:provisioning/detectors/Win32ServiceDetector.adoc[Win32ServiceDetector] to detect Microsoft Exchange services instead.

=== Core, Minion, and Sentinel container images no longer use confd
The Core, Minion, and Sentinel container images render their configuration directly from environment variables and etc overlay files at startup instead of through confd.

For Core, most variable names and defaults are unchanged, but a few things behave differently:

* Five Trapd variables were renamed; the old names still work as a fallback. As before, the Trapd variables are imported into the database only once, when the database is first initialized or upgraded.
* `OPENNMS_NOTIFD_SLACK_CHANNEL` and `OPENNMS_NOTIFD_MATTERMOST_CHANNEL` are no longer supported.
* Boolean and numeric variables are validated, and an invalid value stops the container at startup. `CORE_SERVICE_*_ENABLED` is the exception: {page-component-title} reads it directly, and any value other than `true` disables the service.
* The JMX exporter `config.yaml` is generated only when the exporter is enabled, and a file mounted at the default path is no longer overwritten.

For Minion and Sentinel:

* The `minion-config.yaml` and `sentinel-config.yaml` files are no longer supported, and the container refuses to start if one is present.
* The separate Kafka RPC, Sink, and Twin settings for Minion were dropped; use the `KAFKA_IPC_*` variables for all Kafka communication.
* The `minion-config-schema.yml` file is no longer published.

For details, see:

* xref:reference:configuration/core-docker.adoc#core-oci-confd-migration[Core: Migrating from confd]
* xref:reference:configuration/minion-docker.adoc#minion-legacy-config-migration[Minion: Migrating from `minion-config.yaml`]
* xref:reference:configuration/sentinel-features.adoc#sentinel-confd-migration[Sentinel: Migrating from confd-based images]

=== At least PostgreSQL 14.0 is required

OpenNMS {page-component-title} now requires PostgreSQL 14.x or newer.
If you are running an older version, you must upgrade to PostgreSQL 14 or later.
Attempting a schema upgrade with `install -dis` will result in an error.
If upgrading PostgreSQL to at least version 14 isn’t possible and you’re completely blocked, the -Q flag lets you skip the version check.
Use this only as a last resort, since it may affect compatibility.
Be aware that doing so takes you beyond supported configurations — here be dragons.

=== CitrixDetector removed
The CitrixDetector has been removed.

=== Prometheus RemoteWrite plugin (formerly Cortex TSS plugin)

The OpenNMS Cortex TSS plugin has been renamed to the Prometheus RemoteWrite plugin to reflect that it works with any Prometheus `remote_write`-compatible time series store, not just Cortex.
As part of the rename, the OSGi configuration PID changed from `org.opennms.plugins.tss.cortex` to `org.opennms.plugins.tss.prometheus`.

IMPORTANT: If you previously configured the plugin via `$\{OPENNMS_HOME}/etc/org.opennms.plugins.tss.cortex.cfg`, rename the file to `$\{OPENNMS_HOME}/etc/org.opennms.plugins.tss.prometheus.cfg` after upgrading. If you do not, the plugin falls back to default values and writes will not reach your configured time series store.

The Karaf feature is now `opennms-plugins-prometheus-remotewrite` (previously `opennms-plugins-cortex-tss`), and the KAR file is `opennms-prometheus-remotewrite-plugin` (previously `opennms-cortex-tss-plugin`).
See xref:deployment:time-series-storage/timeseries/prometheus-remotewrite.adoc[the Prometheus RemoteWrite plugin documentation] for details.

=== DominoIIOPDetector removed
The DominoIIOPDetector has been removed.
Remove any detector that uses the class `org.opennms.netmgt.provision.detector.simple.DominoIIOPDetector` from your foreign source definitions before upgrading.
The DominoIIOPMonitor is unchanged; to keep monitoring Domino IIOP, add the DominoIIOP service to nodes in their requisitions, or detect it with a xref:reference:provisioning/detectors/TcpDetector.adoc[TcpDetector] on port 63148.

=== Newts and Cassandra time series storage deprecated

Newts, the time series store backed by Apache Cassandra, should be considered deprecated.
{page-component-title} {page-component-version} still ships with Newts support for existing Newts users: if you are already running on Newts, you can continue to do so through this release.

After {page-component-title} {page-component-version} reaches end of support, OpenNMS will no longer provide official support for the Cassandra backend, and Newts will not be carried forward into subsequent releases.
If you are using Newts, we suggest planning a move to the xref:deployment:time-series-storage/timeseries/prometheus-remotewrite.adoc[Prometheus RemoteWrite plugin], which stores metrics in any Prometheus `remote_write`-compatible time series database.
Note that there is no tool to copy existing Newts data into another store, so after a switch the historical metrics remain in Cassandra until its retention period expires.

=== Jasper Reports engine
We have updated the Jasper Reports engine to version 7.0.7. Custom reports created using version 6.x must be updated to work with the new version.

=== REST API configuration writes require ROLE_ADMIN
Writing OpenNMS configuration through the REST API (`POST`/`PUT`/`DELETE` on `/rest/config/**`, including the alarm northbounder configurations) now requires `ROLE_ADMIN`; previously an account with only `ROLE_REST` could write these.
Update any integration that used a `ROLE_REST` account to change configuration to use a `ROLE_ADMIN` account.
Reading configuration and all other `ROLE_REST` data operations are unchanged.

=== REST API requisition reads require ROLE_PROVISION
Reading requisitions through the REST API now requires `ROLE_PROVISION` or `ROLE_ADMIN`.
Give `ROLE_PROVISION` to integration accounts that read requisitions.

=== Write-only asset fields in the REST API
The asset fields `password`, `enable` and `snmpcommunity` are now write-only in the REST API.

=== Raw SQL query parameter requires ROLE_ADMIN
The raw SQL `query` parameter of the v1 REST API now requires `ROLE_ADMIN`.

=== v2 REST API SNMP interface and topology searches
* `/api/v2/snmpinterfaces`: a search with a `*` wildcard on `ifAlias`, `ifDescr`, `ifName` or `physAddr` now ignores case, the same as the `snmpInterface.*` searches of `/api/v2/nodes`.
A search without `*` is still an exact, case-sensitive match.
* `/api/v2/nodes`: a search without `*` on `snmpInterface.ifAlias`, `snmpInterface.ifDescr`, `snmpInterface.ifName`, `snmpInterface.physAddr` or `topology` now treats `%`, `_` and `\` as literal characters, not as SQL `LIKE` wildcards.
For example, `snmpInterface.ifName==Gi0_1` no longer matches `Gi0X1`.
Use `*` as the wildcard.
`maclike` is not changed: `%` and `_` are still wildcards.

=== Node links point to the new node details page
The `link` field of node resources in the `/rest/resources` and `/rest/graphs` REST APIs now holds the URL of the new node details page, `ui/index.html#/node/<node>`, instead of `element/node.jsp?node=<node>`.
The node part is escaped as one URL path segment, so a `/` in a foreign ID becomes `%2F`.
The link is still relative to the web application context root.
Update integrations that read this field.

The `baseNodeUrl` field of the menu REST API (`/api/v2/menu`) is now `ui/index.html#/node/`.
Plugins append a node ID or `foreignSource:foreignId` to it to link to a node's details page.
Escape the appended part as one URL path segment, for example with `encodeURIComponent`, so that a `/`, `#` or space in a foreign ID does not break the link.
It is a hash route, so do not append query parameters such as `&quiet=true`.

=== Legacy node page removed
The legacy node page, `element/node.jsp`, is removed.
Its URL, `element/node.jsp?node=<node>`, stays available as a redirect to the new node details page, `ui/index.html#/node/<node>`, so existing links, bookmarks and stored event text continue to work.
The redirect ignores all query parameters other than `node`, for example `quiet=true`.
Without a `node` parameter, it goes to the node list.

The new node details page does not show links that plugins add with `ConditionalPageNavEntry` services registered with `Page=node`.
The legacy node page was the only page that showed them.
The built-in "View in Topology" link is replaced by the "Topology Map" item in the "Graphs" menu of the new page.

=== DOCTYPE rejected in requisition and foreign-source XML
Requisition and foreign-source XML that contains a `DOCTYPE` is now rejected on import.
Remove the `DOCTYPE` from requisitions that external tools write, or set the system property `org.opennms.provision.requisition.allowDoctype=true` to accept it.

=== ROLE_MINION no longer reads /rest/config and /rest/info
`ROLE_MINION` no longer gives read access to `/rest/config/**` or `/rest/info`.
Minion does not use these endpoints.
`ROLE_MINION` still gives access to the embedded ActiveMQ broker.

=== Ops Board and Wallboard removed

The Vaadin-based Ops Board (operator board) and Wallboard, their dashlets, and the *Wallboard Configuration* admin page have been removed.
These provided auto-rotating, dashlet-composed displays intended for wall-mounted operations screens.

The *Ops Board* and *Wallboard* main-menu entries and the `admin/wallboardConfig.jsp` page no longer exist, and any existing Ops Board configuration is no longer used.
There is no drop-in replacement.

=== Actiond removed

The `Actiond` daemon and its configuration `etc/actiond-configuration.xml` have been removed. Actiond-related event fields will still validate but are ignored.

=== KSC Reports replaced by Graph Collections

The feature formerly labeled *KSC Reports* is now *Graph Collections* throughout the web UI and the documentation, and its pages have moved to the Vue UI under `ui/index.html#/graph-collections`.
The list, view, editor and the *Add to Graph Collection* dialog on the resource graphs pages are all new; a collection can be created from a blank form, as a copy of another, from the on-the-fly collection of a node, or straight from the dialog when adding a graph.
Graphs built in the custom performance graph builder can be added to a collection too, and are drawn there over the collection's timespan; the REST API carries them as graphs of kind `adhoc`.
The global search category formerly named *KSC Report* is now *Graph Collection*.

The legacy `KSC/*.jsp` pages and `KSC/*.htm` controllers have been removed.
`KSC/index.jsp` and `KSC/customView.htm` redirect to the new list and view pages, with the report, timespan and graph type parameters carried over, so bookmarks and links to a report keep working; the legacy editor URLs do not redirect.
The view page refreshes itself every five minutes, as the legacy page did.
The REST API under `/rest/ksc` has been removed; use the xref:development:rest/graph_collections.adoc[Graph Collections API] under `/api/v2/graph-collections` instead.
The configuration file `etc/ksc-performance-reports.xml` and the `ksc.default.graphsPerLine` property are unchanged, so existing reports keep working.

NOTE: Update any of your own documentation, runbooks, training material, UI automation or API integrations that refer to *KSC Reports*, the `KSC/` page URLs or the `/rest/ksc` endpoints.
