
= Thresholding
:description: Overview of thresholding in {page-component-title} to define limits against a managed entity's performance metrics.

A threshold lets you define limits against a managed entity's network performance metrics.
When a value goes above or below the specified limit, an event is triggered.
The following limit types are supported:

* High
* Low
* Absolute value
* Relative change

== How it works

{page-component-title} uses collectors to collect data for a particular protocol or a family of protocols (SNMP, JMX, HTTP, XML/JSON, WS-Management/WinRM, JDBC).
You can configure individual collectors in a collector package--this essentially defines the set of instructions that drives their behavior.

Collectd gathers and stores performance data from collectors.
This is the data against which {page-component-title} evaluates thresholds.
Thresholds trigger events when specific values are met, and notifications and alarms can be configured for these events.

.Thresholding network diagram
image::thresholding/thresholding-flow.png["Network diagram showing the relationships among thresholding components in {page-component-title}"]

{page-component-title} uses four thresholding algorithms to trigger an event (see xref:quick-start/thresholding.adoc[] in the Quick Start section for more information).
{page-component-title} applies these algorithms against any performance data collected by <<deep-dive/performance-data-collection/introduction.adoc#ga-performance-mgmt, collectd>> or pushed to <<deep-dive/telemetryd/introduction.adoc#ga-telemetryd, telemetryd>>.
This includes, but is not limited to, metrics such as CPU load, bandwidth, disk space, and so on.

For information on setting and configuring collectors, collectd, and `collectd-configuration.xml`, see xref:deep-dive/performance-data-collection/introduction.adoc[].

[[threshold-configuration]]
== Threshold configuration

The thresholding configuration is stored in the database and consists of two parts:

Threshold groups::
A threshold group holds the thresholds and expression-based thresholds evaluated against one RRD repository.
See xref:deep-dive/thresholds/thresh-group.adoc[].

Threshd packages::
A threshd package selects the interfaces to threshold with a filter rule and address ranges.
Each service in the package names the threshold group to apply through its `thresholding-group` parameter.
A threshold group has no effect until a package applies it.
See xref:deep-dive/thresholds/thresh-package.adoc[].

To manage both parts, click menu:Administration[Configure Thresholds] in the side menu, or click menu:Administration[Configure OpenNMS] and then, under *Performance Measurement*, click *Configure Thresholds*.
The page requires the `ROLE_ADMIN` role and has the following tabs:

[options="autowidth"]
|===
| Tab | Description

| Groups
| Create, edit, rename, and delete threshold groups and their thresholds.

| Packages
| Create, edit, and delete threshd packages, their address ranges, outage calendars, and services.

| Upload / download
| Download the threshold groups or the threshd configuration as a JSON or XML file, or replace either of them in full by uploading a file.
|===

Changes take effect when you save them.
You do not need to reload Threshd or restart {page-component-title}.

You can also manage the configuration through the xref:development:rest/thresholds-rest-api.adoc[Thresholds REST API].

NOTE: Earlier versions stored this configuration in `$\{OPENNMS_HOME}/etc/thresholds.xml` and `$\{OPENNMS_HOME}/etc/threshd-configuration.xml`.
During the upgrade, the contents of both files are migrated into the database, and the files are no longer read.
Editing them has no effect.
To apply an existing XML file, upload it on the *Upload / download* tab.
